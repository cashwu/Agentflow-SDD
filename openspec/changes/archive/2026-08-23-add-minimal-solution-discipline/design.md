## Context

本 change 修改 `cash-apply` 的 task loop 與 `cash-propose`／`cash-apply` 共用 review gate。權威與生成關係如下：

- `.claude/skills/cash-apply/SKILL.md` 是 task loop 與 Implementation Notes Protocol 的人工維護源頭；`.agents/skills/cash-apply/SKILL.md` 是生成輸出。
- `scripts/cash-skills/blocks/review-gate.md` 是兩個 workflow 共用 review loop 的人工維護源頭，會注入 `.claude/skills/cash-propose/SKILL.md` 與 `.claude/skills/cash-apply/SKILL.md`，再由 `scripts/cash-skills/generate.fish` 生成兩個 `.agents` 變體。
- `scripts/cash-skills/tests/skill-checks.fish` 已驗證生成 freshness、canonical well-formedness 與部分 load-bearing literals。本 change 必須新增獨立內容斷言，不能只依賴 source／generated byte equality，因為 source 與 output 同時錯誤時 freshness 仍會通過。
- `cash-skills.version` 目前是 `2.15.0`。任何受管 `SKILL.md` byte change 都受 bundle history gate 約束，因此版本、`.cash-skills/lib/cash_cli/installer.py` 的 `BUNDLE_VERSION` 與 `.cash-skills/manifest.tsv` 必須在第一個 skill edit 前同步到 `2.16.0`。

本 change 的核心不是追求最少 LOC，而是讓 agent 在已理解 contract 後，以固定且可稽核的順序選擇最低複雜度、仍完整滿足 observable behavior、interface／data shape、failure modes、acceptance criteria 與安全邊界的實作。

相關 open signals 對本設計的約束：

- `acceptance-asserts-removal-not-replacement`：驗收必須正向斷言新 ladder、Reviewer B lens 與 ceiling fields，而不只斷言不存在舊文字。
- `variant-parity-checks-only-markers`：除生成 freshness 外，兩個變體各自都要接受內容斷言。
- `implementation-notes-protocol-drift` 與 `implementation-deviation-not-backfilled`：ceiling 欄位必須併入既有 append-only protocol 與 reviewer 讀取義務，不建立第二套 ledger。
- `version-bump-sequenced-after-guarded-edits`：版本同步任務排在第一個 skill edit 之前。

## Goals / Non-Goals

**Goals**

- 讓每個 `cash-apply` task 在寫 code 前執行同一套 ordered minimal-solution ladder。
- 為所有 ladder 候選定義 contract／safety eligibility gate 與 deterministic tie-break。
- 讓既有 Reviewer B 在不增加 agent 或狀態機的情況下辨識由 artifacts 或 changed diff 引入的不必要複雜度。
- 讓已依既有 protocol 記錄、且替代機制具有非平凡已知 ceiling 的 `deviation` 同時保存限制與可驗證的重訪條件。
- 以正向與負向機械斷言保護上述 contract，並維持 source／generated ownership 與雙 variant 對等。

**Non-Goals**

- 見 proposal `## Non-Goals`。尤其不新增 skill、reviewer、round type、mode、source comment ledger、LOC gate 或測試減量規則。

## Decisions

### D1：階梯只選擇機制，不得推翻 artifact scope

minimal-solution ladder 在 agent 已重新讀取 task、相關 spec、Implementation Contract 與實際 call flow 後執行。它的第一個 gate 是 scope eligibility：候選方案必須完整滿足 task 與 contract；如果 task 與 contract 衝突、行為不在 scope、或要求不清楚，沿用既有 unclear-task／blocker triage，MUST NOT 以 YAGNI 名義自行跳過 pending task。

通過 eligibility gate 後，按以下順序停止在第一個成立的 rung：

1. `reuse`：codebase 已有 helper、type、module 或 established pattern。
2. `stdlib`：語言 standard library 已完整涵蓋。
3. `native`：platform／framework／database native feature 已完整涵蓋。
4. `installed-dependency`：既有已安裝 dependency 已完整涵蓋，且不新增 dependency。
5. `custom`：只寫滿足 contract 的最小、清楚 custom implementation。

「一行」不是 rung。所有候選都先接受同一 eligibility gate：observable behavior、interface／data shape、failure modes、acceptance criteria、trust-boundary validation、data-loss prevention、security 與 accessibility 不得減損。`clarity 永遠優先於 brevity` 保持既有優先順序。

### D2：tie-break 必須可預測且不建立新 blocker 分支

若多個候選都符合 eligibility gate，先選序位較早的 rung。同一 rung 內有多個成本相當候選時，依序選 edge-case correctness 較強、再選較符合既有 codebase pattern 者。只有仍無法依此判定、且答案可能改變 contract／scope 時才進既有暫停分支；多個都保留 contract 的內部選擇不新增 pause 條件。

若此選擇源自「原設計手段不可行、替代手段保持 contract」的 blocker triage，仍須依既有規則寫 `deviation`；階梯與 tie-break 不取代、不重排、不擴張 blocker triage。逐字片語 `a synchronization primitive, identity/generation type, or state machine not defined in design.md` 在 task loop 與 review loop 兩處保持不變。

### D3：complexity review 是 Reviewer B 的 lens，不是新角色

修改 shared review gate 中 Reviewer B 的角色文字：

- cash-propose：除既有 missing risks、unstated assumptions、scope gaps 外，檢查 proposal／design／tasks 是否要求或默許 `new dependency`、`single-implementation abstraction`、`pass-through wrapper`、`speculative configuration`、`duplicate existing capability`，或可由 `stdlib`／`native` 解決的 custom mechanism，且 artifacts 未說明這些複雜度為 contract 所需。
- cash-apply：除既有 logic bugs、boundary error handling 與 spec example edge cases 外，只針對 changed diff 檢查上述六類複雜度；不得把 pre-existing code 或 unrelated refactor 納入 finding。

此 lens 沿用既有 finding schema、severity、confidence、introduced_by、false-positive filter、decision 與 cumulative blocking set。Reviewer 不以預估 LOC 作為 finding 或 severity 依據。full round 仍恰好兩位 reviewers，micro round 仍恰好一位 Reviewer V。

### D4：ceiling 是 deviation 的條件式補充欄位

既有 entry 的四個固定欄位保持不變。當且僅當一筆依既有規則已必須記錄的 `deviation` 所採替代手段具有非平凡、真實且已知的 ceiling，才在 `原因` 後追加且必須成對出現：

```md
- 限制：<不影響目前 contract、但會使機制不再適用的具體上限>
- 重訪條件：<可觀察或可衡量、達成時應重新設計的 trigger>
```

ceiling 可以是 scale、resource、contention、latency、platform 或 algorithmic bound，但不得描述已違反目前 observable behavior、failure mode、安全或驗收標準的缺陷；那種情況不是合格的 contract-preserving substitute，應走既有暫停分支。`重訪條件` 不得使用「之後需要時」「規模變大時」等沒有 observable threshold 的空泛文字。

沒有非平凡已知 ceiling 時不新增這兩欄，也不填 `none`。routine implementation、ordinary tradeoff、同 contract 內的小判斷仍不得建立 note。`open-question` shape 不變。Reviewer A 與 Reviewer V 沿用既有義務讀取整份 notes，並額外把缺一欄、trigger 不可觀察、或 ceiling 已侵害 contract 視為 justified-deviation 評估的一部分。

### D5：生成、版本與測試順序

實作順序固定：

1. 將 `cash-skills.version`、`.cash-skills/lib/cash_cli/installer.py` 的 `BUNDLE_VERSION` 與 `.cash-skills/manifest.tsv` 同步到 `2.16.0`。
2. 在單一不可分割 task 內修改 `.claude/skills/cash-apply/SKILL.md` 與 `scripts/cash-skills/blocks/review-gate.md`，執行 `scripts/cash-skills/generate.fish` 產生兩份 `.agents` skill 與重新注入後的 `.claude/skills/cash-propose/SKILL.md`，然後在任何下一次 Cash CLI invocation（包括 `task done`）之前立即執行 `PYTHONPATH=.cash-skills/lib python3 -s -P -B -m cash_cli.installer --self` 發布與最終 skill bytes 一致的 manifest。此 task MUST NOT 與其他 task 平行，避免共享工作樹暴露 portable manifest digest drift 或互相覆寫 manifest。
3. 在 `scripts/cash-skills/tests/skill-checks.fish` 新增正／負向 contract tests。
4. 再次重建 final manifest，執行 skill suite、bundle history test 與 Cash validation。

不得直接人工編輯 `.agents` generated outputs。若 `2.16.0` 已被其他變更占用，實作時改用嚴格高於當前值的最小 patch version，並依 Implementation Notes Protocol 記錄 deviation。

## Implementation Contract

### C1：minimal-solution ladder

- 觀察行為：`cash-apply` 兩個變體在每個 task 寫 code 前，先完整理解 artifact 與 call flow，再依 `reuse` → `stdlib` → `native` → `installed-dependency` → `custom` 順序選擇第一個通過 eligibility gate 的方案。
- scope boundary：pending task 不得因 YAGNI 或「contract 沒明寫」被靜默略過；task／contract 衝突仍走既有 unclear-task handling。
- safety boundary：任何 rung 都不得弱化 observable behavior、interface／data shape、failure modes、acceptance criteria、trust-boundary validation、data-loss prevention、security 或 accessibility。
- clarity boundary：不得新增「one line」rung，且 `clarity 永遠優先於 brevity` 保持不變。
- acceptance：兩個變體皆含五個 exact rung identifiers 與完整 eligibility／understanding clauses；tests 對任一 rung 的缺失、順序交換、較早 rung 不合格時繼續規則缺失、YAGNI 處置反轉、任一 safety eligibility 項缺失或 `one line` rung 注入皆以非零結束。

### C2：deterministic tie-break 與 blocker triage 保留

- 觀察行為：跨 rung 候選選較早 rung；同 rung 成本相當時依 edge-case correctness、existing codebase pattern 順序裁決。
- scope boundary：多個保留 contract 的內部選擇不暫停；答案可能改變 contract／scope 時沿用暫停分支。
- invariants：blocker triage 兩個互斥分支、fallback precedence、`deviation` 義務與逐字 circuit-breaker 片語不變。
- acceptance：skill tests 正向斷言完整 tie-break clause 與 circuit-breaker 片語兩處存在，並以 mutation 證明交換 edge-case correctness／existing codebase pattern 次序會失敗；pause branch／continue branch 原有 load-bearing literals保持。

### C3：Reviewer B complexity lens

- 觀察行為：shared Reviewer B contract 對 cash-propose artifacts 與 cash-apply changed diff 檢查六類：`new dependency`、`single-implementation abstraction`、`pass-through wrapper`、`speculative configuration`、`duplicate existing capability`、`stdlib`／`native` replacement opportunity。
- scope boundary：只報告本 proposal 引入或本 apply diff 引入的複雜度；pre-existing、unrelated、明確由 contract 要求或已有 rationale 的內容不報。
- state-machine boundary：full／micro reviewer 數量、roles、round types、finding fields、confidence filter、introduced_by 與 decision derivation完全不變。
- metric boundary：LOC、預估 token／cost／time 不得成為 finding 或 gate input。
- acceptance：shared source block與四個注入後的 canonical skill 各含 complexity lens；tests 斷言六類字面值、cash-propose artifact scope、cash-apply changed-diff-only scope、完整 exclusions 與 metric boundary clauses存在，Reviewer A／B／V 數量 contract 保留；mutation 移除任一 scope／exemption clause或把 LOC／token／cost／time 改成 gate input時失敗，且不存在 `net: -`、`LOC gate` 或第三 reviewer 角色。

### C4：已知 ceiling deviation shape

- 觀察行為：只有既有 protocol 已要求的 `deviation` 且替代手段具有非平凡已知 ceiling 時，entry 才追加成對的 `限制` 與 `重訪條件`。
- data shape：兩欄置於 `原因` 後且成對出現；`open-question` 與無已知 ceiling 的 deviation 維持四欄 shape。
- validation semantics：`重訪條件` 必須可觀察或可衡量；ceiling 必須位於目前 contract acceptance envelope 之外。若 ceiling 已破壞目前 contract，不得記完繼續，必須依既有 blocker triage 暫停。
- reviewer semantics：Reviewer A／V 把缺欄、不成對、空泛 trigger 或侵害 contract 納入 deviation justification 評估，不新增新的 decision branch。
- acceptance：兩個 apply 變體含 conditional fields、四欄保留與 Reviewer A／V 對 fields／trigger／contract envelope 的完整評估文字；tests 以正向 exact clauses 與負向 fixture 證明 routine implementation 不建立 note、known-ceiling fixture 缺任一欄時失敗、空泛 trigger 不被接受，且 contract-invasive ceiling 不得記錄後繼續並必須導向 `$cash-ingest`。

### C5：ownership、parity 與版本

- `.claude` 與 shared block 維持權威源頭；`.agents` 只能由 generator 產生。
- `cash-apply` 兩 variant 的 task-loop／notes 段落，以及四個 canonical skills 的 shared review block，在 invocation prefix 正規化後逐 byte 相同。
- bundle version 三處一致，`2.16.0` 嚴格高於 `2.15.0`，且 managed skill source edit、generation 與 manifest publication 位於同一不可分割 task；任何下一次 Cash CLI invocation 前，manifest records 已對應生成後 bytes。
- acceptance：`fish scripts/cash-skills/tests/skill-checks.fish all`、`python3 scripts/cash-skills/tests/test_bundle_version_history.py` 與 `.cash-skills/bin/cash validate add-minimal-solution-discipline` 全部通過。

## Risks / Trade-offs

**階梯變成閱讀捷徑。** Agent 可能看到 `stdlib` 就停止理解實際 flow。D1 明定 ladder 在 artifact 與 call flow 閱讀之後執行，tests 正向釘住 understanding guard。

**階梯與 task authority 衝突。** 原始 Ponytail 的 YAGNI rung 可以拒絕需求，但 `cash-apply` 的工作是履行已核准 artifacts。D1 把 scope eligibility 定義為 conflict detector，不允許靜默跳過 task。

**complexity lens 產生 scope creep。** Reviewer 可能要求清理整個 repository。D3 限定 proposal-introduced／changed diff，並沿用現有 pre-existing 與 unrelated false-positive 規則。

**簡化 ceiling 被誤當成可接受的 contract 缺陷。** D4 要求 ceiling 位於目前 acceptance envelope 之外；已影響 contract 的替代方案必須暫停，不得靠 note 合法化。

**可觀察 trigger 很難完全機械判斷。** tests 能把關欄位存在與明顯空泛字樣，語意品質仍由 Reviewer A／V 評估。這是刻意保留的人類／agent judgment，不新增 parser 或 schema engine。

**修改自身 grader。** proposal `## Impact` 已逐一宣告四個 protected canonical skill、shared block、skill tests 與 master spec；未宣告的 protected paths 仍不得在 review fix actions 中修改。

**managed skill 修改造成 CLI fail closed 的中間狀態。** portable manifest 會在 `SKILL.md` bytes 改變後、重建前拒絕任何 Cash CLI command。D5 將所有 managed skill edit、generation 與 `--self` publication 合併成單一不可分割 task，且禁止平行 dispatch；task 只在 manifest 恢復一致後呼叫 `task done`。
