## 1. 測試先行

- [ ] 1.1 在 `scripts/cash-cli/tests/test_runtime_and_errors.py` 新增 **Help flag 列出全部 command**、**缺少 command 時指向 help**、**Handler 層的 unknown_command 不受影響** 與 **Help flag 不改變其他位置的行為** 的失敗測試：斷言 `--help` 與 `-h` 各自 exit 0 且輸出涵蓋全部 dispatch table key；斷言 `--json` 輸出的 `commands` 欄位逐元素等於排序後的 dispatch table key 序列——期望值直接由 runtime 匯入該 table 後排序取得，不得在測試內另寫靜態清單，也不得只斷言集合相等（`COMMANDS` 的插入順序與排序後不同，只比對集合會讓違反排序 MUST 的實作通過）；斷言非 `--json` 為人類可讀文字；斷言不帶 argument 時以 `missing_command`、未知 command 時以 `unknown_command` 失敗，訊息指向 help flag 且不內嵌 command 清單，code 與 exit code 皆不變；斷言未知 new mode（須以 `new bogus <artifact-id>` 這類帶第二個 argument 的形式觸發——`new bogus` 只有一個 argument 時會先落在 `invalid_arguments`）與未知 discipline 的訊息既不含 top-level 清單也不指向 help，且語意不變。這兩項必須自行建立暫存 workspace 並在測試內 `os.chdir` 進去（以 `addCleanup` 還原原 cwd，因為本檔是 in-process 測試，chdir 會污染同 process 的其他 case）。workspace 須以 `tempfile` 建立、`git init` 過，並寫入內容有效的 `.cash.yaml` 與 `openspec/config.yaml`（`schema: spec-driven`）——這兩個只建空檔會先失敗於 `config_invalid`。`.cash-workspace.lock` 的要求相反：它必須是**空檔**且 mode 恰為 `0644`（須顯式 `os.chmod(..., 0o644)`，勿依賴 umask），寫入任何內容或非 `0644` 都會先以 `workspace_lock_invalid` 失敗（已實測：缺檔得「missing or unsafe」、有內容得「must be an empty 0644 regular file」、空的 `0644` 才到達 `unknown_command`）。`CASH_PROJECT_ROOT` 不是 workspace 來源而是一致性守衛：`Workspace.discover` 以 cwd 經 `git rev-parse --show-toplevel` 決定 root，只設該環境變數而不 chdir 會得到 `workspace_root_mismatch` 而非 `unknown_command`（已實測）；若要設它，其值必須等於該暫存 git root。可沿用 `scripts/cash-cli/tests/test_negative_atomicity.py` 的 `LauncherLockTests.setUp` 之 `tempfile` 加 `git init` 加 `addCleanup` 骨架，但不得整段照抄——該樣板的 `.cash.yaml` 與 `.cash-workspace.lock` 是由它執行 installer 產生的，本任務不走 launcher／安裝路徑，這兩個檔須自行建立。理由：`create.py` 與 `discovery.py` 都在 mode／discipline 判定之前先解析 workspace，依賴呼叫者 cwd 會讓斷言結果不穩定，也不得對真實 repository workspace 執行 recover；斷言 `list --help` 仍交給 `list` handler 且不輸出 help。以 `scripts/cash-cli/tests/test_runtime_and_errors.py` 驗證這些測試在實作前失敗。
- [ ] 1.2 在 `scripts/cash-cli/tests/test_negative_atomicity.py` 新增 **Help 不繞過 receipt gate** 的 characterization test（回歸鎖，非 red-green；本節其餘 task 為測試先行，此項是明確例外）：斷言 receipt 缺失或內容無效的已安裝 target 上，以 `--help` 作為第一個 argument 執行 launcher 維持既有的 `bootstrap_invalid` 或 `receipt_invalid` 與 exit 1，且不輸出 help。放在此檔而非 `scripts/cash-cli/tests/test_runtime_and_errors.py` 的理由：這兩個 code 只由 launcher 產生、需要真實安裝的 target，而後者目前是零 subprocess 的純 unit test；本檔的 `LauncherLockTests` 已有可沿用的安裝 setUp 樣板。此為 characterization test 而非 red-green test：該斷言描述的正是變更前的現況（launcher 先驗 receipt，`--help` 在 receipt 無效時必然 exit 1，且當時本就沒有 help 輸出），因此它在實作前後皆通過。它的作用是回歸鎖——確保實作 help 時沒有人為了讓 fresh clone 也能用 help 而把分流點移到 `validate_receipt` 之前。以 `scripts/cash-cli/tests/test_negative_atomicity.py` 驗證該測試在實作前後皆通過。
